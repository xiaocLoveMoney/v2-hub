# 02 · 总体架构

## 1. 系统拓扑

```
                                         ┌──────── 独立服务器（docker compose）────────┐
3x-ui A (:2053) ┐                        │  Caddy :443（前置 Cloudflare 代理）          │
3x-ui B (:2053) ┼── HTTPS + Bearer ──────┤   ├─ /api/*、订阅地址 → hub-server :8080    │
3x-ui C (:2053) ┘   （hub-server 主动调）│   ├─ /admin/*         → MinIO 桶 web-admin  │
                                         │   └─ 其它             → MinIO 桶 web-user   │
                                         │  hub-server ── PostgreSQL                    │
                                         │            └─ MinIO（上传文件）              │
                                         └──────────────────────────────────────────────┘
代理客户端（Mihomo / sing-box / v2rayN）── 拉订阅 → https://域名/{订阅前缀}/{token}
                                       └─ 代理流量直连各 3x-ui 节点，不经过 v2-hub
```

单域名，管理端在 `/admin/` 子路径（Ruling-61）。

M11 起 hub-server 另经 SSH（默认 22 端口）主动连接托管的主机，用来安装面板与做固定的几种运维动作（Ruling-68，docs/03 §5.22）；给主机申请公开证书时 hub-server 还会访问 DNS 服务商的 API（Cloudflare）建解析；证书由主机上的 acme.sh 申请，主机要能访问 ACME 签发方（默认 Let's Encrypt）与 DNS 服务商的 API（Ruling-72 – Ruling-74）。
SSH 只承载这些控制面操作：不建隧道、不转发端口，面板接口仍走上图的 HTTPS + Bearer。

## 2. 铁律

### 铁律一：v2-hub 只做控制面（Ruling-4）
代理流量永远不经过 v2-hub 服务器。验：compose.deploy.yml 只开放 80/443；hub-server 无任何代理协议监听。

### 铁律二：面板是入站配置的事实来源
平台对入站的增删改都先写面板、成功后回同步落库；定时同步发现面板侧被直接改动时标记“漂移”提示，不静默覆盖。
验：IT 用例在面板侧直接改入站后，平台显示漂移。

### 铁律三：业务层与面板实现解耦（Ruling-8）
`service` 只依赖 `manager/panel` 的 `Provider` 接口与中立模型；差异用 `Capabilities` 表达，上层按能力开关功能，
不按面板类型写分支。验：`grep -r "/panel/api" internal/service` 无结果；service 测试只用 fake Provider。

### 铁律四：订阅请求不回源面板
订阅只读平台库里的缓存（节点参数、用户凭据、链式规则），面板宕机不影响已有订阅下发。

### 铁律五：期望状态 + 对账
用户授权变更只改平台库里的期望状态；对账器比对各面板实际 client，按差异调用 Provider，幂等可重试。
禁止在 Web 请求里同步逐台改面板。

## 3. 一次核心业务的完整数据流（给用户开通）

1. 管理员在管理端给用户分配套餐 → `POST /api/admin/users/{id}/plan` → service 写 `user`、`user_grant`（期望状态），写审计日志。
2. 事件触发对账器（另有定时兜底）：按服务器分组，算出“该用户应在哪些入站上”与面板实际 client 的差异。
3. 对账器经 `Provider.UpsertClient / AttachClient / DetachClient` 写各面板；结果写 `provision`（成功 / 失败 / 重试次数）。
4. 流量任务定时 `Provider.ListClientTraffic` 汇总到 `traffic_snapshot`，超额或到期 → 改期望状态为禁用 → 对账器 `SetClientsEnabled(false)`。
5. 用户客户端拉 `/sub/{token}`：hub-server 读库 → 分享链接解析为 `ProxyNode` → 叠加链式规则 → 按 UA / 参数渲染格式。

## 4. 技术选型理由

| 模块 | 选型 | 为什么 | 不选什么 |
|---|---|---|---|
| hub-server | Go 1.27 + 标准库 net/http + slog | 单二进制部署；并发轮询多面板用 goroutine + 限流；Mihomo / sing-box / Xray 生态同为 Go | Java（部署重）、Python（长期并发轮询需额外投入） |
| 数据库 | PostgreSQL 17 | JSONB 存面板原始入站配置；INET 类型；单库可用外键（Ruling-9） | MySQL |
| 前端 | React 19 + TS + Vite 8，两个独立应用 | 管理侧与用户侧受众、权限、发布节奏不同（Ruling-10） | 单应用多入口 |
| 静态资源 | MinIO（pgsty 发行版）+ Caddy | 前端与 hub-server 独立发布；Caddy 自动 HTTPS（Ruling-6、Ruling-61） | Go embed、Nginx |

## 5. 契约与版本纪律

- 契约只在 `v2-hub-contract/`；破坏性变更同一 PR 改引用方（Ruling-3）。
- 版本 tag `vX.Y[.Z]`：破坏性升 Y，additive 升 Z。
- 生成物各模块自持入库、不互相 import（Ruling-1）。
- 支持的 3x-ui 版本以 `upstream/3x-ui/` 快照为准（Ruling-7）；升级基线 = 拉新快照 + 跑契约测试。

## 6. 镜像与生产部署（Ruling-62、Ruling-109）

| 项 | 约定 |
|---|---|
| 镜像 | 两个，均为 `linux/amd64` + `linux/arm64`，同时推到 Docker Hub `xiaoclux/<名称>` 与 GHCR `ghcr.io/xiaoclovemoney/<名称>`：`v2-hub-server`（`v2-hub-server/Dockerfile`）；`v2-hub-init`（`v2-hub-contract/deploy/init/Dockerfile`，构建上下文为仓库根），一次性容器，内含两个前端的 `dist`、`init.sql` 与迁移，依次做迁移 → 上传桶 `uploads` 与只写账号（Ruling-89）→ 发布前端到桶 `web-admin` / `web-user`（Ruling-6），成功即退出，hub-server 等它成功才启动 |
| 标签 | `sha-<完整提交号>`、`edge`：`main` 每次检查全绿后；`vX.Y`、`latest`：推 `vX.Y` tag 时（工作流 `release`）。开源用户用 `latest` 或固定版本，生产用 `sha-<提交号>` |
| 构建 | 工作流 `images`（可复用）：GitHub 托管机上 buildx + QEMU，GHCR 用 `GITHUB_TOKEN` 推；Docker Hub 用仓库 Secrets `DOCKERHUB_USERNAME` / `DOCKERHUB_TOKEN`，未配置时只推 GHCR、不挡部署；Docker Hub 的仓库简介取自 `.github/dockerhub/README.md`。PR 改到 Dockerfile 或 init 目录时只构建 amd64、不推送 |
| 编排 | 开源用户与生产同用 `v2-hub-contract/deploy/compose.deploy.yml` + `caddy/Caddyfile`；镜像仓库与标签取 `HUB_IMAGE_REGISTRY`（默认 `docker.io/xiaoclux`）/ `HUB_IMAGE_TAG`（默认 `latest`），`.env` 模板是 `deploy.env.example`，可用 `init_env.sh deploy.env.example .env` 填随机密码 |
| 触发 | `main` 有推送时，工作流 `deploy` 先调用三个模块的检查（server / admin-web / user-web），全部通过后构建并推送镜像，再进入部署；Actions 页可手动触发。每套环境同一时间只跑一个部署，不取消进行中的；一套失败不影响另一套 |
| 执行者 | 每套生产环境一台机器，各跑一个自托管 Runner（系统用户 `github-runner`，在 docker 组），标签一套一个，列在 `deploy.yml` 的 `matrix.runner-label`；目前只有一套 `v2-hub-prod`（第二套 `v2-hub-prod-b` 已于 2026-11-26 撤下，机器与 Runner 都已清理）。各环境数据库、凭据、域名互相独立。只有 `main` 能触发；PR 的检查全部在 GitHub 托管机上跑 |
| 新增一套环境 | Docker（含 compose 插件 ≥ 2.17）、`git`、`flock`；建 `github-runner` 用户并加入 docker 组；防火墙只开 SSH、80、443（含 udp）；建 `/opt/v2-hub/.env`；在仓库 Settings → Actions → Runners 注册 Runner，标签取一个新值（不能与已有环境同标签，否则部署被随机派给其中一台），以 `svc.sh install github-runner` 装成服务；把标签加进 `matrix.runner-label` |
| 凭据 | 只在生产机 `/opt/v2-hub/.env`（600，属 `github-runner`），首次装机时随机生成；不进仓库，不进 GitHub Secrets。拉 GHCR 镜像用的是工作流自带的 `GITHUB_TOKEN`（只读 packages），部署结束即 `docker logout` |
| 步骤 | `v2-hub-contract/deploy/deploy_prod.sh`：同步编排文件到 `/opt/v2-hub` → `.env` 缺上传账号时补上（Ruling-89）→ 把本次的镜像仓库与标签写进 `/opt/v2-hub/image.env` → 拉镜像 → （仅首次升级）导入旧迁移状态文件 → `docker compose up -d`（先跑 init，成功后更新 hub-server）→ 重载 Caddy → 健康检查 → 清理旧镜像 |
| 迁移 | 由 `v2-hub-init` 执行，记录在库内表 `hub_deploy_migrations`：空库执行 `init.sql`，并把镜像里所有 `migrations/*.sql` 记为已执行；之后每次只执行表里没有的迁移，按文件名顺序，执行成功才记入。库非空却没有记录表时拒绝执行（防止对老库重放迁移）；老生产机首次升级时由 `deploy_prod.sh` 把 `/opt/v2-hub/state/applied-migrations` 导入表中，并改名为 `applied-migrations.imported` |
| 健康检查 | 经 Caddy 容器访问 `hub-server:8080/healthz`，最多等 60 秒；失败则工作流失败（不自动回滚：把 `image.env` 的 `HUB_IMAGE_TAG` 改回上一个 `sha-…` 再 `compose up -d` 即可，旧镜像保留最近几个） |
| 手动操作 | `cd /opt/v2-hub && docker compose -f compose.deploy.yml --env-file .env --env-file image.env <子命令>`，下文“命令前缀”即此 |
| 首次装机后 | 建超级管理员：在生产机执行 `<命令前缀> run --rm --no-deps -it --entrypoint /app/hub hub-server admin-create -f /app/etc/hub-server.yaml -username <名称>`，密码无回显输入。库里还没有所有者时，这个超管即所有者（Ruling-99）；它第一次登录后须先开启两步验证才能用其它功能（Ruling-98） |
| 管理员恢复 | 只在生产机上执行、不经 HTTP，审计的操作者记为系统（docs/03 §4.3 命令行）。命令前缀同上（`<命令前缀> run --rm --no-deps -it --entrypoint /app/hub hub-server`），子命令：`admin-owner-set -f /app/etc/hub-server.yaml -username <名称>` 指定或转移所有者（目标须是启用状态的超管）；`admin-totp-reset ... -username <名称>` 清除两步验证并吊销其全部会话（所有者遗失验证器时用）；`admin-password-reset ... -username <名称>` 重设密码并吊销其全部会话，口令无回显输入两次，不出现在命令行参数里。上线 Ruling-95 – Ruling-100 后先核对所有者（迁移 0025 回填为最早创建的启用超管），不对就用 `admin-owner-set` 转移 |
| Cloudflare | SSL/TLS 模式须为“完全（严格）”；Caddy 用 HTTP-01 申请证书（Cloudflare 对 `/.well-known/acme-challenge/` 不做 HTTPS 跳转） |
